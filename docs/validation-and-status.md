## 使用后反馈

仅在实际任务/阶段使用记忆或 Skill，且存在真实验收物时，记录最小反馈到原报告旁：

- 当前项目与任务/阶段身份。
- 原 bank/event/source hash，或准确获准 Skill 的路径/hash。
- applied / rejected / considered 的使用自报。
- 实际交付物与验证证据引用。
- 原身份是否独立核验、来源缺口和验证限制。

不记录逐轮对话、推理或逐检索轨迹。格式和 hash 能验证结构与字节完整性，不能证明语义真实、独立接受或因果收益。缺少有效对照时，`causal_benefit` 固定为 `unproven`，不能据此声称省 tokens 或提速。反馈不自动写银行、修改旧记忆或安装 Skill。

## 可迁移验收清单

1. **身份**：两个同名项目不会互相取证；搬迁后旧 scope 不会被默认为新身份。
2. **证据**：只出现一次的重要限制能被找到；中段修订不会被尾部摘要覆盖；失败尝试不能被写成成功。
3. **讨论状态**：可以找回尚未确认的想法，同时不把它当作正式决定。
4. **隐私**：正文投影排除推理、工具日志和未获准内容；台账没有标题或正文；敏感候选不出包。
5. **预算**：seed、元数据页和补读累计计数；重启不清额度；超限拒绝而非截断。
6. **一致性**：全部交付来源在写前复核，来源漂移使当前尝试失效；承认跨服务仍有竞态限制。
7. **恢复**：丢失回执、超时和取消都协调原事件；unknown 不自动重试，不把进程退出当作远端停止。
8. **Skill**：已有覆盖不重复制作；证据不足不起草；草稿不进入发现目录、不自动执行。
9. **采用**：分别验收文件安装、进程加载、真实触发、最终收据及用户接受。

## 怎样检验是否更好

两组对照先共用同样的授权、隐私和来源准入。基线按固定顺序给获准资料；候选路线在同一范围内选择相关完整证据并按需补读。保持模型/设置、任务、可用修订和评分标准一致；不能故意让基线拿不到重要条件或发送越权资料。

先看承重证据覆盖、过期事实误用、冲突保留、越界率、正确拒答、Skill 重复率，再衡量总输入输出、检索与复核成本、失败/恢复成本及用户体验。字节减少不等于 token、费用或质量改善。

早期合成对照确实减少了一些无关材料，但缩减依赖固定无关来源；另一次短对话的阶段卡组装反而比完整原文更大。因此没有默认新增一套阶段卡或新索引服务，也没有发布节省百分比。
