# 架构与五层职责

## 五层是职责，不是五个数据库

| 层 | 职责 | 主要载体 | 避免的问题 |
| --- | --- | --- | --- |
| L0 | 原始证据 | 原始会话、权威项目文件、版本历史 | 摘要丢掉一次出现的重要限制 |
| L1 | 当前工作桥接 | 当前上下文、必要时有界交接 | 新对话不知道当前目标、待办和来源入口 |
| L2 | 可信长期事实 | 受政策约束的 Hindsight 银行 | 把高频猜测、旧状态或聊天原文当事实 |
| L3 | 产物与方法 | 原产物、索引、runbook、Skill | 重复造工具或把所有产物塞进提示词 |
| L4 | 使用后学习 | 实际任务验收记录与受控纠正 | 仅凭 Agent 自报就认定记忆有用 |

Notion 横跨讨论导航和产物索引：保存候选、分歧、问题状态和来源入口。它能够记录“讨论发生过”，不必先证明某个方案正确。它的派生记录不覆盖原始证据，历史计划也不是当前执行授权。

这里没有按出现次数提升事实可信度的机制。一次明确的限制不能因为低频而消失；错误重复很多次也不会因此更可信。日期或频率只能在另行验证后作为调度参考，不能替代来源核实。

## 三条路径

**正常任务路径**：当前上下文与项目文件 → 必要时定向召回 → 核实原始条件 → 执行与验收 → 最小留存审查。

**归档路径**：检测新归档元数据 → 精确目标证据投影 → 同一 worker 联合审核记忆和 Skill → 分别准入。手动点击归档本身没有可靠的即时审核 hook，因此使用已批准的周期检测补足机会。

**使用后反馈路径**：实际使用且存在任务验收物 → 在原报告旁绑定最小反馈 → 必要时提出追加纠正或 Skill 修订。没有每次检索都记录的跟踪器，也没有反馈自动写银行。

## 多 Agent 边界

各 Agent 固定写自己的银行。已授权的互读必须绑定相同规范项目身份或明确配对主题，并核对原记录来源；不能把互读理解成互写、复制或自动合并。冲突保留并显式呈现。

项目重命名、搬迁或重新克隆时重新绑定身份。文件系统定位能帮助确认项目位置，却不能证明授权或原会话归属。

DSH 与 Codex 共享的是设计思路和有范围的协作。归档 worker 与后期来源补读/验收反馈的本地部署只覆盖一个 Codex 项目，不能宣称已在 DSH 全量接通。历史上讨论过的独立补审路径 B 保持禁用；不要把 B 与后来的普通归档 worker 混为同一条路径。

## 可信度与权限分开

当前用户授权决定可以做什么；原始来源决定过去说过或验证过什么；长期记忆帮助找到这些来源。任何检索结果、历史计划或 Skill 都不能自己授予新的权限。

同样需要分开的状态包括：文件已保存、进程已加载、工具实际调用、事件已入队、远端完成、用户接受。文件更新不能证明旧会话热加载；通知发出不能证明用户看见。
